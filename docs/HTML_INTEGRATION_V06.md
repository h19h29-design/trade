## 등록 흐름

직접 등록은 `물품 올리기 → 조달청 정보로 등록 시작 → 목록번호/식별번호/품명 입력 → 조회 → 실제 제품과 비교 → 선택한 정보 입력 → 부서/수량/상태 → 비공개 초안 저장`이다. 원본 대장 번호와 현물 조달번호를 자동으로 같다고 보지 않는다.

엑셀 등록은 `파일 → 시트/열/기본부서 확인 → 미리보기 → 비공개 초안 등록 → 사진의 대상 행·현물·개인정보 확인 → 사진 연결 → 조달청 일괄 보완 → 게시 검토`이다. 파일에서 기관명이 확인되면 로그인 기관과 대조하며 불일치하면 중단한다. 기관을 클라이언트 선택값으로 변경하지 않는다. 동일 물품이라도 부서·회계·결정이 다르면 나누며, 결정번호 없는 행은 자동 합치지 않는다.

번호·금액·날짜 원문은 parsed workbook/raw 행과 원본 자산/묶음 snapshot으로 남긴다. 파일 원본 바이트 전체를 보관하는 기능은 아니다. 16자리 목록번호를 숫자 셀로 저장한 파일은 정밀도 손실 가능성 때문에 원본 번호를 대조하고 텍스트 셀로 저장하도록 안내한다.

## 사진의 구분

엑셀 삽입사진은 실제 현물을 찍은 사진인지 확인한 것만 `PHOTO`에 연결한다. 위치가 가까운 행을 임의로 찾거나 여러 행을 자동 선택하지 않는다. 여러 행에 걸치거나 겹친 사진은 담당자가 행을 지정한다. XLS의 사진, IMAGE 함수, 외부 URL, 절대위치 앵커, SVG/EMF/WMF 등은 지원하지 않는다. 표 데이터는 계속 가져올 수 있고 사진은 별도 업로드한다.

조달청 이미지는 `catalog_images`에 출처·식별번호·해시·확인자와 함께 별도 저장한다. **현물사진이 아니며 게시용 PHOTO·증빙 수량에 포함하지 않는다.** 서버 이미지 이용조건 설정과 사용자의 참고사진 연결 확인이 모두 필요하다. 개별 후보에서 선택해 연결하며, 대량 조회가 사진을 무조건 일괄 게시하지는 않는다.

사진 후보는 30장, 각 압축 이미지2MB/전체8MB까지만 추출하고 서버에서 재인코딩한다. 엑셀 파일 자체는8MB/2000행/64열 범위를 유지한다. 숨김 시트와 외부 이미지 관계는 읽지 않는다. 비공개 사진은 같은 기관 업무계정만 읽는다.

## 조달 API 계약과 키

2026-11-03 공공데이터포털의 실제 Swagger를 조회해 아래 계약을 확인했다.
- 문서: https://www.data.go.kr/data/15129417/openapi.do
- HTTPS 경로: `apis.data.go.kr/1230000/ao/ThngListInfoService02/getThngPrdnmLocplcAccotListInfoInfoPrdlstSearch02`
- 필수: `serviceKey`, `pageNo`, `numOfRows`. 식별번호는 `prdctIdntNo`, 품명은 `krnPrdctNm`.
- JSON/XML 응답과 XML 인증실패를 구분하고, 출력에 요청 URL·키·원문 오류본문을 내보내지 않는다.

원본 HTML의 대문자 ServiceKey 주장과 달리, 이번 확인한 Swagger는 **serviceKey**다. 기본값은 공식 명세를 따르고 승인받은 API 명세가 다른 경우에만 `PROCUREMENT_KEY_PARAM=ServiceKey`를 명시적으로 선택한다. 두 파라미터를 무작정 보내지 않는다. URL 인코딩된 키는 한 번 디코딩한 뒤 안전하게 인코딩한다.

`DATA_GO_KR_SERVICE_KEY`는 서버에만 두며 브라우저·localStorage·VITE 변수·공개 저장소에 넣지 않는다. 외부 실호출은 실제 키와 활용신청이 있는 로컬/NAS에서 Codex가 확인한다. 이 작업에서는 real-key 호출하지 않았다. RAG DeepSeek 및 기존 사진 AI 설정은 별개이며 변경하지 않았다.

## 대량 조회·빈칸 반영

최대50묶음을 순차 조회하고 초안만 대상으로 한다. 중단은 현재 요청 이후 추가 호출을 막는 방식이며 현재 네트워크 요청의 즉시 취소는 아니다. 같은 번호·품명은 캐시를 재사용한다. 성공 캐시 기본6시간, 검색결과 없음5분, 오류는 캐시하지 않는다. 동시 외부조회2개, 기관 일일300/전체800회(서울 날짜) 기본 상한이다. 실제 서비스 승인 한도에 맞춰 낮추거나 조정한다. 재시도 실패도 사용량에 포함한다.

번호 일치 후보에 대해 사용자가 빈칸 반영 버튼을 눌러야 제조사·모델·설명·현물번호·분류명이 채워진다. 이름검색 후보는 개별 확인한다. 원본 품명·번호·수량·불용결정·게시승인과 이미 작성된 값은 일괄 덮어쓰지 않는다. API에 모델·치수·중량이 없으면 만들어 넣지 않는다. 제품 식별번호 일치가 대장-현물 일치를 보증하지 않는다.

## 재고 화면의 의미

`대장 수량`, `등록 수량`, `신청 가능`을 구분했다. 등록 수량은 등록 당시 조사·엑셀 기록이지 인계 후 현재 실물 보유량 확정치가 아니다. 신청 가능은 게시/불용증빙 검토 상태에서 예약·인계·완료 배정을 제외한 수량이다. 부서별 표에서 수량을 임의로 직접 고치는 기능은 넣지 않았다. 기존 대량 상태입력과 예약·인계 보존 규칙을 따른다.

## 운영·데이터 보존

사업 DB schema v2에서 v3로 추가 마이그레이션한다. 신규4개 테이블은 import_images, catalog_cache, catalog_usage, catalog_images다. 기존 기관·계정·물품·파일·자산·예약 테이블을 재생성하지 않는다. 추가 BLOB은 기존 SQLite 백업에 포함된다. RAG corpus/usage DB는 여전히 별도 백업 대상이다.

업데이트 전 앱·DB·첨부의 일관된 백업과 새 경로 복원 검증이 필요하다. 새 스키마에서 문제가 생겼을 때 이전 이미지로만 되돌리지 않는다. 이전 버전은 v3 DB를 거부하므로, 검증한 업데이트 전 백업을 **새 경로에 복원**해 이전 이미지와 연결한다. 현재 DB는 삭제하지 않는다.
